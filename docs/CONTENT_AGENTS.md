## **1. Почему именно три роли**

Сегодня контент делается одним потоком: один и тот же проход решает, *чему*
учить, пишет текст, придумывает упражнения и сам же считает результат
годным. Последствия уже измерены и записаны в `docs/plan-tasks.md`:

| Что сломалось | Чья это была нерешённая ответственность |
| ----- | ----- |
| Уровень CEFR проставлен по книге, а не по главе — «A City of Bridges» и «A Small City» обе A2 | **Learning** — решение об уровне не было отдельным шагом с критерием |
| Банк теста весь про собеседования: тест меряет знакомство с темой, а не язык | **Learning** — не было ограничения «тематически нейтрально» до генерации |
| У собственных текстов нет внешней проверки; уровни проставлены суждением автора | **QA** — роли не существовало |
| `missionFromContent` жёстко ставит 5 заданий, AI-генератор допускает 5–40 минут | **Learning** — бюджет урока не был входом для генератора |
| Определение «…where you go **into a** building» дошло до Postgres как синтаксис | **Content** — агент писал SQL вместо данных (§5.4) |

Разделение — не «больше агентов», а разрезание одной перегруженной
ответственности по трём естественным швам:

1. **Learning** отвечает на вопрос *чему учить и как мы поймём, что научился*;
2. **Content** — *как выглядит конкретное задание, которое к этому ведёт*;
3. **QA** — *действительно ли это задание проверяет тот навык и ту цель*.

**Почему не один агент.** Автор не может быть независимым судьёй своей работы —
это принцип 7 фреймворка, уже применённый к коду (`AGENT_FRAMEWORK.md §7`,
«Независимый reviewer»). Для контента он весит больше, чем для кода: у кода есть
`tsc`, у формулировки задания механической проверки нет вообще.

**Почему не шесть.** Дробить Content на vocabulary/grammar/dialogue/speaking —
это специализация по типу артефакта, а не по ответственности. Разница между
«написать fill_blank» и «написать multiple_choice» — это Skill, не Agent
(`AGENT_FRAMEWORK.md §4`, принцип 10). Ростер расширяется только если появится
ответственность, которой ни у кого нет, — не когда появится новый тип задания.

## **2. Место в существующем ростере**

`AGENT_FRAMEWORK.md §9` фиксирует 4 агента: `frontend-builder`,
`supabase-engineer`, `design-system-agent`, `qa-agent`. Три новых агента
добавляются **по другой оси**, и это надо назвать явно, иначе выглядит как
нарушение решения 2 из §14:

```
Ось 1 — кто строит приложение:  frontend-builder · supabase-engineer · design-system-agent · qa-agent
Ось 2 — кто производит материал: learning-agent · content-agent · content-qa-agent
```

Агенты оси 1 пишут код, который *рендерит* контент. Агенты оси 2 не пишут
продуктовый код вообще — они производят строки в `content_units`,
`knowledge_items`, `generated_exercises`, `assessment_questions`,
`roadmap_modules`. Пересечения Boundaries нет ни в одной точке.

**`content-qa-agent` ≠ `qa-agent`.** Существующий `qa-agent` (§9) — про
Maestro/Playwright/Jest и Integration-check: работает ли экран. Новый — про
педагогику: годное ли это задание. Разные Knowledge, разные критерии, разные
режимы отказа. Слить их — значит потребовать от одного агента одновременно
знать Expo и CEFR. Имя выбрано с префиксом, чтобы `Agent` tool не путал их.

**Кто применяет SQL к базе.** Никто из трёх. Они производят файлы; SQL из них
собирает детерминированный скрипт (§5.4); применяет — Orchestrator или
`supabase-engineer`, когда тот будет формализован. Это прямое следствие
`TZ.md` Правила 3 в применении к контенту: агент, пишущий учебный текст, не
имеет доступа к продовой базе.

## **3. Три режима одного пайплайна**

Роли одни и те же, вход разный. Все три режима реальны и уже нужны сегодня.

### **3.1 `authored` — спецификация вперёд, текст следом**

Закрывает дыры покрытия, которых нет ни в одном учебнике с подходящей
лицензией (`plan-tasks.md`, этап 1: `clothing` пуст, B2+ не покрыт ничем).

```
пробел в покрытии → LEARNING SPEC → текст + knowledge_items + exercises → QA → validated
```

Провенанс жёсткий и уже зафиксирован решением от 2026-08-28:
`source_url = 'yuny://authored/en/v1'`, `parser = 'authored'`,
`origin = 'ai_generated'` у **всего**, включая примеры. Лицензия
проприетарная — сгенерированный текст не выдаётся за материал открытого
учебника.

### **3.2 `imported` — текст дан, спецификация выводится**

Для уже импортированных глав Open Oregon: 103 главы лежат в `content_units`,
из них извлечение `knowledge_items` не отработало ни разу
(`onboarding-v2.md §9.1`).

```
content_unit (parsed) → LEARNING SPEC (что эта глава реально может дать) → извлечение → QA → validated
```

Отличие от 3.1 в границах: Learning Agent здесь **не выбирает** тему и уровень
свободно — он их *устанавливает по тексту* и обязан обосновать измеримо
(§7, Skill `cefr-calibrate`). Content Agent при этом ограничен `origin =
'source_derived'` для всего, что есть в тексте буквально, и обязан пометить
`ai_generated` всё, что дописал сам (определение, пример) — граница уже
закодирована в CHECK-констрейнте `knowledge_items.origin`.

### **3.3 `assessment-bank` — задания для измерения, а не для обучения**

Решение от 2026-08-28: банк теста наполняется генерацией, а не поиском книг.
Выход — `assessment_questions`, не `generated_exercises`.

```
непокрытая полоса (B1+) → LEARNING SPEC (полоса × навык × нейтральная тема) → вопросы → QA → validated
```

Критически другое ограничение от Learning Agent: задание должно быть
**тематически нейтральным** и калиброванным по сложности, иначе повторится
уже случившаяся ошибка — тест мерил знакомство с темой собеседований.

## **4. Ответственность и границы**

### **4.1 Матрица прав на запись**

Единственный надёжный способ не перепутать три ответственности — таблица «кто
чем владеет». Всё, чего нет в строке агента, ему запрещено.

| Артефакт / поле | learning-agent | content-agent | content-qa-agent |
| ----- | :---: | :---: | :---: |
| `content/specs/*.spec.json` | **владеет** | читает | читает |
| `content_units.cefr_level` | **решает** | — | оспаривает |
| `content_unit_topics` (привязка к теме) | **решает** | — | оспаривает |
| `roadmap_modules` (состав, порядок, `why`) | **решает** | — | оспаривает |
| `content/drafts/*.content.json` | читает | **владеет** | читает |
| `content_units.parsed_blocks` (текст) | — | **пишет** | оспаривает |
| `knowledge_items` (`data`, `dedup_key`) | — | **пишет** | оспаривает |
| `generated_exercises.payload` | — | **пишет** | оспаривает |
| `assessment_questions` (prompt/options/correct_index) | — | **пишет** | оспаривает |
| `assessment_questions.difficulty`, `cefr_level` | **решает** | переносит как есть | оспаривает |
| `content/reviews/*.review.md` (вердикт) | читает | читает | **владеет** |
| `status: draft → validated` | — | — | **владеет** |
| `supabase/seed-*.sql` | — | — | — (генерируется скриптом, §5.4) |
| `TZ.md`, `docs/*.md`, миграции, код приложения | — | — | — |

«Оспаривает» = может выпустить `REVISION_REQUIRED` с указанием на поле, но не
может изменить его сам. Это и есть независимость QA: у него нет права правки
ни на одном артефакте, который он оценивает.

### **4.2 LEARNING AGENT**

**Главный вопрос:** чему пользователь должен научиться и как мы поймём, что
научился?

**Отвечает за:**
- Goal → Scenario: развернуть цель (`goals.title`, `target_situations`) в
  конкретную учебную ситуацию, в которой навык применяется;
- Skill (`public.skill`: speaking/listening/vocabulary/grammar/reading/writing)
  и Sub-skill (свободная формулировка внутри навыка);
- Learning Objective — проверяемое утверждение о том, что ученик сможет
  делать; не «изучить лексику отеля», а «выбрать нужное слово из
  hostel/guesthouse/hotel по описанию ситуации»;
- User Level и Difficulty: полоса CEFR (`content_units.cefr_level`,
  `assessment_questions.cefr_level`) и `difficulty` 1–5; **на уровне единицы
  контента, а не книги** — это прямое исправление известного дефекта;
- Assessment Criteria: что считается доказательством достижения LO — сколько
  и каких заданий, что явно **вне** проверки;
- отбор тем и порядок модулей карты (`onboarding-v2.md §6`), включая жёсткое
  правило: модуль допускается только если на нужной полосе **есть материал**;
- бюджет: размер урока 3–5 заданий на 5–7 минут (`onboarding-v2.md §7.1`) —
  это вход генератора, а не его свободный выбор.

**Не делает:**
- не пишет ни текста, ни формулировки задания, ни вариантов ответа, ни
  определений слов — «Learning Agent НЕ создаёт финальные упражнения»;
- не оценивает готовый контент (это отдельная роль — иначе он судья
  собственной спецификации);
- не меняет каноническую таксономию тем (21 тема, этап 2) без вынесения
  предложения на утверждение — таксономия описывает, что нужно ученику, а не
  что удобно сгенерировать;
- не решает, каким пользователям это достанется, — Learning State и выбор
  следующей миссии остаются серверной логикой (`TZ.md §3`, Правило 1). Агент
  проектирует *материал*, не runtime-решение.

### **4.3 CONTENT AGENT**

**Главный вопрос:** как создать конкретное задание, которое помогает достичь
Learning Objective?

**Отвечает за:** учебный текст (`parsed_blocks`), `knowledge_items`
(vocabulary/grammar/topic/example), `generated_exercises`
(multiple_choice/fill_blank), вопросы банка, объяснения и примеры, шаблоны
feedback-копирайта под `TZ.md §14` — всё строго внутри рамок спецификации.

**Не делает:**
- **не меняет Learning Objective, Skill, уровень, тему и состав курса.** Если
  спецификация невыполнима (нет слов нужной частотности на этой полосе, LO
  требует навыка, которого нет рендерера) — останавливается и возвращает
  `SPEC_INFEASIBLE` с причиной. Не «поправлю сам, автор поймёт»;
- не пишет SQL. Выход — JSON (§5.2). Причина конкретна и стоила четырёх
  падений заливки: текст, попавший в SQL напрямую, ломает синтаксис
  (`into a` → `relation "a" does not exist`). Экранирование — работа скрипта,
  не языковой модели;
- не помечает свой результат как готовый: `status` остаётся `draft`, флаг
  `validated` физически вне его прав;
- не изобретает провенанс: в режиме `imported` цитата помечается
  `source_derived`, дописанное — `ai_generated`. Смешать — значит выдать
  сгенерированное за материал учебника;
- не трогает код приложения и Edge Functions. Если нужный тип задания
  клиент не рендерит (`CLIENT_RENDERABLE_TYPES` в `_shared/mission.ts`) —
  это Open Question в Handoff, а не повод писать рендерер.

### **4.4 CONTENT QA / EDITOR AGENT**

**Главный вопрос:** действительно ли это качественное задание, которое
проверяет нужный навык и соответствует цели пользователя?

**Отвечает за:** вердикт `APPROVED` / `REVISION_REQUIRED` с конкретными
замечаниями (§10.2), и за единственное изменение состояния во всём пайплайне —
перевод `draft → validated`.

**Не делает:**
- **не правит контент.** Ни одной строки, даже очевидной опечатки. Иначе
  следующая версия частично написана рецензентом, и независимость потеряна.
  Опечатка — это `REVISION_REQUIRED / minor`;
- не переписывает спецификацию. Если дефект в ней («LO непроверяем»,
  «difficulty не соответствует полосе») — вердикт адресуется Learning Agent,
  а не Content Agent, и это отдельный тип замечания (§9.3);
- не видит рассуждений Content Agent и его Memory (§9.4) — только
  спецификацию и результат. Судит артефакт, а не намерение;
- не одобряет частично. `APPROVED` — про весь пакет; один блокер = весь пакет
  на доработку.

## **5. Артефакты и контракты**

### **5.1 Файловая раскладка**

```
content/                                   ← новый каталог, версионируется в git
├── specs/<slug>.spec.json                 ← learning-agent
├── drafts/<slug>.content.json             ← content-agent
├── reviews/<slug>.review.md               ← content-qa-agent, раунды дописываются снизу
└── approved/<slug>.content.json           ← побайтовая копия драфта на момент APPROVED

supabase/seed-<batch>.sql                  ← генерируется из approved/, вручную не правится
scripts/content-schema.mjs                 ← формы артефактов + машинные проверки (§10.1)
scripts/content-emit.mjs                   ← approved/*.json → идемпотентный SQL
scripts/content-validate.mjs               ← машинные проверки (§10.1)
```

`<slug>` один для всей цепочки — `travel-a2-booking-01`. По имени файла видно,
какая спецификация породила какой драфт и какое ревью; ничего не надо
восстанавливать по содержимому.

`approved/` иммутабелен: правка после одобрения — это новый `spec.version` и
новый проход, а не молчаливое редактирование одобренного. Без этого «APPROVED»
ничего не гарантирует.

### **5.2 Learning Specification — выход Learning Agent**

```jsonc
{
  "spec_id": "travel-a2-booking-01",
  "version": 1,
  "mode": "authored",                     // authored | imported | assessment-bank
  "goal_context": {
    "goal_family": "travel",              // семейство целей, не goal одного пользователя
    "target_situations": ["booking a room online", "checking in at a guesthouse"],
    "topic_slug": "travel-and-accommodation",   // обязан существовать в public.topics
    "module_kind": "topic"                // topic | foundation
  },
  "scenario": {
    "description": "Учащийся бронирует жильё онлайн и заселяется",
    "register": "service / neutral",
    "constraints": ["без названий брендов", "без цен, привязанных к стране"]
  },
  "level": {
    "cefr": "A2",
    "difficulty": 2,                      // 1..5, ложится на assessment_questions.difficulty
    "calibration_basis": [                // измеримо, а не «на глаз»
      "средняя длина предложения ≤ 12 слов",
      "≥ 90% словоформ — из списка A1–A2",
      "не более 2 новых грамматических точек"
    ]
  },
  "skill": "vocabulary",                  // public.skill
  "sub_skills": ["accommodation nouns", "comparatives of price"],
  "learning_objectives": [
    {
      "id": "LO-1",
      "statement": "Учащийся выбирает правильное слово для типа жилья по описанию ситуации",
      "knowledge_kind": "vocabulary",     // knowledge_items.kind
      "target_keys": ["hostel", "guesthouse", "budget", "included", "confirmation"],
      "assessment": {
        "evidence_of_success": "4 из 5 целевых слов выбраны верно в контексте, без подсказки",
        "exercise_types": ["fill_blank", "multiple_choice"],
        "min_exercises": 5,
        "distractor_rules": [
          "дистракторы — реальные слова из этой же единицы",
          "никакие два варианта не синонимичны"
        ],
        "out_of_scope": ["орфография", "произношение"]
      }
    }
  ],
  "content_budget": {
    "unit_word_count": [150, 260],
    "tasks_per_lesson": [3, 5],           // onboarding-v2.md §7.1
    "exercises_per_objective": [1, 3]
  },
  "provenance": {
    "origin": "ai_generated",
    "source_url": "yuny://authored/en/v1",
    "license": "Proprietary — Yuny original content"
  },
  "coverage_rationale": "travel-and-accommodation: 4 главы (A2, B1); clothing пуст; B2+ не покрыт"
}
```

`coverage_rationale` — не украшение. Правило отбора из `onboarding-v2.md §6`
(«только темы, у которых реально есть контент на нужных полосах») проверяемо
только если решение записано вместе с данными, на которых принято.

### **5.3 Content Draft — выход Content Agent**

Форма зеркалит строки БД, чтобы эмиттер был чистым отображением без логики:

```jsonc
{
  "spec_id": "travel-a2-booking-01",
  "spec_version": 1,
  "content_unit": {
    "external_id": "authored-booking-a-room",
    "title": "Booking a place to stay",
    "cefr_level": "A2",                   // копия из спецификации, менять запрещено
    "topics": ["travel-and-accommodation"],
    "parsed_blocks": [{ "type": "paragraph", "text": "..." }],
    "word_count": 177
  },
  "knowledge_items": [
    {
      "objective_id": "LO-1",             // ← звено цепочки прослеживаемости
      "kind": "vocabulary",
      "dedup_key": "budget",
      "origin": "ai_generated",
      "data": { "word": "budget", "definition": "the amount of money you can spend" }
    }
  ],
  "exercises": [
    {
      "objective_id": "LO-1",
      "knowledge_dedup_key": "budget",
      "type": "fill_blank",
      "payload": {
        "sentence_with_blank": "Marta cannot pay 120 euros because she has a small ___.",
        "accepted_answers": ["budget"]
      }
    }
  ]
}
```

### **5.4 Эмиссия SQL — детерминированный скрипт, не агент**

```
approved/<slug>.content.json  →  scripts/content-emit.mjs  →  supabase/seed-<batch>.sql
```

Скрипт отвечает за: экранирование строк, идемпотентные `on conflict do update`
по существующим уникальным ключам (`content_units(source_id, external_id)`,
`knowledge_items(content_unit_id, kind, dedup_key)`,
`generated_exercises(knowledge_item_id, type)`), простановку
`status = 'validated'` только для одобренного, и нарезку вывода на куски
12–14 КБ (`plan-tasks.md`: в куске такого размера виновная строка находится за
минуту, в файле на 66 КБ — нет).

Сторож на SQL-ключевые слова, добавленный вручную после четырёх падений,
переезжает сюда и становится обязательным шагом, а не памятью автора.

### **5.5 Цепочка прослеживаемости и чего для неё не хватает в БД**

Требование задания:

```
Goal → Skill → Learning Objective → Exercise → Assessment
```

В файлах цепочка держится на `spec_id` + `objective_id`. В базе **рвётся**:
у `content_units`, `knowledge_items`, `generated_exercises` и
`assessment_questions` нет ни одного поля, указывающего на спецификацию.
Следствие практическое: живущее в проде задание нельзя переспросить «а что ты
вообще должно было проверять», и QA не может перепроверить контент после
изменения спецификации.

**Предложение (миграция, требует утверждения — §13):**

| Таблица | Колонка | Зачем |
| ----- | ----- | ----- |
| `content_units` | `spec_id text` | какая спецификация породила единицу |
| `knowledge_items` | `objective_id text` | какой LO закрывает |
| `generated_exercises` | `objective_id text` | какой LO проверяет |
| `assessment_questions` | `spec_id text`, `objective_id text`, `cefr_level`, `knowledge_item_id` | последние две уже запланированы этапом 3 |

Все nullable: существующие 103 главы импортированы без спецификаций, и
задним числом их не выдумывают.

### **5.6 `status` — гейт, у которого сегодня нет зубов**

`knowledge_items.status` и `generated_exercises.status` уже имеют значения
`draft | validated`. Проверено: **ни один потребитель их не читает** —
`missionFromContent()` (`supabase/functions/_shared/mission.ts:318,326`)
выбирает `knowledge_items` и `generated_exercises` без фильтра по `status`.
То есть неодобренный черновик сегодня попадает пользователю ровно так же, как
одобренный.

Это делает `APPROVED` физически значимым, а не декларативным:

- `content-emit.mjs` ставит `validated` только тому, что прошло QA;
- `missionFromContent()` и генератор банка добавляют
  `.eq("status", "validated")`.

**Порядок соблюдён:** сначала первая одобренная партия
(`supabase/seed-authored-clothing.sql`), потом фильтр. Фильтр включён
2026-08-28 в `missionFromContent()`.

Одна деталь, которая всплыла только при реализации и которую дизайн не
предусматривал: фильтровать нужно **до** выбора главы, а не после. Функция
брала самую старую неиспользованную главу и уже потом смотрела на её материал —
с фильтром это значило бы, что первая непроверенная глава закрывает собой все
проверенные, стоящие за ней, и контентный путь тихо умирает. Теперь список
пригодных единиц собирается первым запросом, и «самая старая» выбирается уже
среди них.

**Цена, которую надо назвать вслух:** весь ранее залитый материал (103 главы
Open Oregon и первая authored-партия) имеет `status = 'draft'` и с этого
момента в миссии не попадает. Ничего не ломается — `mission-generate`
откатывается на `generateMission` (проверено по коду: `fromContent ? … :
generateMission(...)`), — но контентный путь работает только на том, что прошло
QA. Это осознанный размен: выдавать ученику непроверенный материал — ровно та
проблема, ради которой пайплайн строился. Ретро-проверка старого материала —
задача, записанная в `docs/plan-tasks.md`.

## **7. Skills**

По `AGENT_FRAMEWORK.md §4` Skill создаётся при первой реальной необходимости, а
не пакетом заранее. Ниже — каталог с явной пометкой, что нужно сразу, а что
ждёт второго применения.

| Skill | Что делает | Кто использует | Когда |
| ----- | ----- | ----- | ----- |
| `content-seed-emit` | `approved/*.json` → идемпотентный SQL, экранирование, нарезка 12–14 КБ, сторож против утечки прозы в синтаксис | Orchestrator | **не нужен как Skill** — это `scripts/content-emit.mjs`, детерминированный скрипт с одним правильным ответом. Оформлять процедуру вокруг него — обёртка ради обёртки (прецедент: `slice-mascot.mjs` тоже не стал Skill'ом) |
| `content-qa-check` | Прогон чек-листа §10.2 по спецификации и драфту, оформление вердикта | content-qa-agent | **не нужен как Skill** — чек-лист уже живёт в §10.2 и в карточке агента. Третья копия нарушила бы принцип 11 (не дублировать знание) |

Возврат полосы + обоснования | learning-agent, content-qa-agent (для проверки) | **первый на очереди** — потребность подтверждена: оба замечания по уровню в первом ревью были нарушениями калибровки, заявленной самой спецификацией. Блокирует его отсутствие частотной базы: нужен либо список первых ~1000 слов, либо база, собранная из уже размеченного материала A1–A2 |
| `topic-coverage-report` | Тема × полоса → сколько единиц, сколько упражнений, сколько `validated`. Отчёт, на котором строится и отбор модулей карты, и приоритет следующей партии | learning-agent | **после подключения к базе** — сейчас покрытие меряется вручную и записано в `plan-tasks.md`; автоматизировать имеет смысл, когда сеть до Supabase перестанет отваливаться |
| `learning-spec-scaffold` | Каркас `spec.json` с обязательными полями и напоминанием про `out_of_scope` | learning-agent | после первых 2–3 ручных спецификаций, когда станет видна устойчивая форма |
| `exercise-draft` | Генерация набора упражнений под один LO с соблюдением `distractor_rules` | content-agent | по мере необходимости |
| `bank-item-draft` | То же для `assessment_questions`, с требованием тематической нейтральности | content-agent | к этапу 5 плана |

у рецензента разные линейки, спор об уровне неразрешим.

**Что показала реализация.** Два Skill'а из четырёх, помеченных «сразу», при
попытке их написать оказались не нужны: один свёлся к скрипту, второй — к
разделу, который уже существует в двух местах. Это ровно то, ради чего
`AGENT_FRAMEWORK.md §4` требует создавать Skill по первой реальной
необходимости, а не планировать каталог заранее: каталог, написанный до работы,
на треть состоит из того, чего не понадобится.

## **8. Memory**

Структура по `AGENT_FRAMEWORK.md §3`, без изменений:

```
.claude/memory/
├── learning-agent/{working,episodic,semantic,decision,feedback}.md
├── content-agent/{working,episodic,semantic,decision,feedback}.md
├── content-qa-agent/{working,episodic,semantic,decision,feedback}.md
└── shared/cross-agent.md
```

Что для контента специфично — **что именно туда попадает**:

| Агент | Что накапливает | Пример записи |
| ----- | ----- | ----- |
| learning-agent | какие формулировки LO оказались непроверяемыми; какие полосы систематически переоценивались; какие темы пусты и почему | «LO вида „познакомиться с лексикой X“ трижды получал REVISION_REQUIRED: непроверяем. Формулировать через наблюдаемое действие» |
| content-agent | повторяющиеся замечания QA; приёмы, которые проходили с первого раза; ловушки формата | «Дистракторы-синонимы — самая частая причина возврата (4 из 9 раундов)» |
| content-qa-agent | классы дефектов и их частота; пороги, по которым выносился блокер; ложные срабатывания | «Пропуск: „Which topic is this?“ формально валиден, но не проверяет никакой LO. Добавить в чек-лист пункт „задание проверяет язык, а не память о тексте“» |
| shared/cross-agent.md | только то, что нужно ≥ 2 агентам | «`clothing` пуст; следующая партия — туда», «B2+ не покрыт ничем» |

**Правила, снимающие два конкретных риска:**

1. **Memory QA не течёт обратно в Content.** Обобщения рецензента доступны ему
   самому и Orchestrator-у; Content Agent получает конкретные замечания
   раунда, а не «список того, на чём тебя обычно ловят». Иначе автор начинает
   оптимизировать под рецензента — проходить проверку, а не учить.
2. **Memory не становится учебной нормой.** «Три раза подряд для A2 работала
   длина предложения ≤ 12» — это Candidate Insight, а не правило. В `TZ.md`
   или `onboarding-v2.md` оно попадает только через Promotion
   (`AGENT_FRAMEWORK.md §11`) с подтверждением пользователя. Memory не
   заменяет документацию проекта.

## **9. Взаимодействие и Handoff**

### **9.1 Основной поток**

```
USER GOAL / пробел в покрытии
        ↓
   LEARNING AGENT ────────────────► content/specs/<slug>.spec.json
        ↓
   [gate A: LearningSpecSchema + topic существует + LO проверяемы]
        ↓
   CONTENT AGENT ─────────────────► content/drafts/<slug>.content.json
        ↓
   [gate B: машинные проверки §10.1 — до QA, не после]
        ↓
   CONTENT QA / EDITOR ───────────► content/reviews/<slug>.review.md
        ↓
   APPROVED ──► approved/<slug>.content.json ──► content-seed-emit ──► SQL ──► база (status=validated)
```

Gate B стоит **перед** QA намеренно: внимание рецензента — самый дорогой
ресурс пайплайна, и тратить его на «в fill_blank два пропуска» — расточительство.
Механическое ловит скрипт, педагогику — агент.

### **9.2 Цикл доработки**

```
REVISION_REQUIRED ──► content-agent (тот же spec, те же границы) ──► gate B ──► QA (раунд N+1)
```

**Лимит — 2 раунда доработки.** На третьем `REVISION_REQUIRED` пакет
останавливается и уходит пользователю с обоими вердиктами и драфтами. Причина:
если после двух проходов замечания не сходятся, дефект почти всегда не в
контенте, а в спецификации или в самом требовании — и ещё один круг его не
найдёт, а токены сожжёт.

### **9.3 Возврат на уровень выше**

Отдельный, не менее важный путь: QA обнаружил, что дефект в спецификации.

```
QA ──[SPEC_DEFECT]──► Orchestrator ──► learning-agent (новая версия spec) ──► content-agent (заново)
```

Симметрично: Content Agent, столкнувшись с невыполнимой спецификацией,
возвращает `SPEC_INFEASIBLE` — и не пытается «поправить по месту». Оба этих
исхода поднимают `spec.version`; драфт против устаревшей версии спецификации не
рецензируется (`gate B` это проверяет).

### **9.4 Правило независимости**

Три механических требования, без которых «независимый QA» — просто слово:

1. `content-qa-agent` запускается **отдельным вызовом `Agent`**, никогда не
   `subagent_type: "fork"` — форк унаследовал бы контекст автора вместе с его
   обоснованиями;
2. в промт QA идут только `spec.json`, `draft.content.json` и отчёт машинных
   проверок — не Handoff Content Agent-а, не его Memory, не его рассуждения;
3. у `content-qa-agent` в `tools:` нет `Write`/`Edit` на `content/drafts/**`.
   Он пишет только `content/reviews/**` и `content/approved/**`. Право правки —
   единственная надёжная гарантия того, что рецензент не станет соавтором.

### **9.5 Шаблоны Handoff**

Базовый шаблон — `AGENT_FRAMEWORK.md §8`. Ниже — обязательные добавления по
ролям (остальные поля шаблона без изменений).

**learning-agent → Orchestrator:**
```markdown
**Spec:** content/specs/<slug>.spec.json (version N, mode: authored|imported|assessment-bank)
**Learning chain:** Goal <...> → Skill <...> → LO-1 <...> → Assessment <...>
**Level & basis:** A2 · difficulty 2 · <на чём основана калибровка>
**Coverage rationale:** <почему эта тема и эта полоса именно сейчас>
**Explicitly out of scope:** <что этот пакет не проверяет — чтобы QA не требовал лишнего>
```

**content-agent → Orchestrator:**
```markdown
**Draft:** content/drafts/<slug>.content.json (против spec version N)
**Coverage of objectives:** LO-1 → 5 items / 6 exercises · LO-2 → ...
**Provenance:** source_derived: X · ai_generated: Y
**Machine gate:** scripts/content-validate.mjs — pass/fail (+ что именно)
**Deviations:** <ничего, что меняет spec; если пришлось — SPEC_INFEASIBLE и стоп>
```

**content-qa-agent → Orchestrator:**
```markdown
**Verdict:** APPROVED | REVISION_REQUIRED | SPEC_DEFECT   (раунд N из 3)
**Checklist:** 10 пунктов §10.2 — pass/fail по каждому
**Findings:**
- [blocker] LO-1 / exercise `budget`: <что не так> → <что должно стать иначе>
- [major]   ...
- [minor]   ...
**Что проверено не было:** <честно: произношение, аудио, культурная уместность вне компетенции>
```

## **10. Validation**

Три уровня, по возрастанию стоимости. Каждый следующий запускается, только
если предыдущий чист.

### **10.1 Машинный (`scripts/content-validate.mjs`, gate B)**

Ни одна из этих проверок не требует суждения — значит, не должна доходить до
агента:

- `ContentDraftSchema.parse` и совпадение `spec_version` с текущей версией spec;
- каждый `objective_id` в драфте существует в спецификации; каждый LO набрал
  свой `min_exercises`;
- `dedup_key` уникален внутри единицы (совпадает с уникальным индексом БД —
  иначе заливка молча перезапишет строку);
- `fill_blank`: ровно один `___`; `accepted_answers` непуст; **правильный ответ
  не встречается в самом предложении** (иначе задание решается копированием);
- `multiple_choice`: ≥ 3 варианта, все уникальны, `correct_index` в диапазоне,
  правильный вариант не самый длинный систематически (дешёвая эвристика против
  подсказки формой);
- `word_count` в границах `content_budget`; число заданий в границах
  `tasks_per_lesson`;
- `origin` соответствует режиму (`authored` → всё `ai_generated`);
- тип задания входит в `CLIENT_RENDERABLE_TYPES` — иначе контент пройдёт
  `activity-submit` и упадёт на `MissionTaskSchema.parse()` у клиента;
- сторож SQL-ключевых слов перед эмиссией.

### **10.2 Педагогический (`content-qa-agent`)**

Десять проверок из задания, переведённые в вопросы, на которые можно ответить
да/нет по конкретному артефакту:

| Проверка | Вопрос по артефакту |
| ----- | ----- |
| correctness | Есть ли ровно один бесспорно правильный ответ? Нет ли второго варианта, который тоже проходит? |
| naturalness | Так говорят? Предложение звучит как речь, а не как заполненный шаблон? |
| level | Лексика и грамматика внутри полосы `spec.level.cefr` — по той же линейке `cefr-calibrate`, что использовал автор спецификации? |
| difficulty | `difficulty` спецификации соответствует реальной трудности задания, а не только полосе текста? |
| skill alignment | Задание проверяет `spec.skill`, а не соседний? (Классика: «vocabulary», который на деле меряет reading) |
| goal alignment | Ситуация задания принадлежит `goal_context.target_situations`, а не абстрактному учебнику? |
| clarity | Инструкция понятна с первого чтения, без второго толкования? |
| ambiguity | Есть ли контекст, в котором дистрактор становится правильным? |
| pedagogical value | Ученик, решивший это, продвинулся к LO — или просто вспомнил текст? Задание учит **языку**, не памяти о прочитанном |
| assessment quality | `evidence_of_success` действительно наступает, если ученик решит эти задания? Не меньше и не больше |

Плюс два пункта, которых в общем списке нет, но которые для Yuny обязательны:

- **тон** (`TZ.md §14`): warm · encouraging · concise; ни одной формулировки
  вида «WRONG» / «FAILED» в объяснениях и feedback-шаблонах;
- **провенанс**: помеченное `source_derived` действительно есть в исходном
  тексте буквально; ничего сгенерированного не выдано за цитату.

### **10.3 Интеграционный (Orchestrator)**

- SQL применяется к базе без ошибок и **идемпотентен**: повторный прогон не
  создаёт дублей и не затирает `validated` обратно в `draft`;
- `mission-generate` на этом материале выдаёт миссию, которая проходит
  `MissionSchema.parse()` на клиенте;
- отчёт покрытия (`topic-coverage-report`) сдвинулся ровно туда, куда
  обещала спецификация.

## **11. Что этот дизайн чинит из уже известного**

Не гипотетические выгоды — конкретные строки из `docs/plan-tasks.md`:

| Известная проблема | Чем закрывается |
| ----- | ----- |
| Уровень по книге, а не по главе | `cefr-calibrate` + `level.calibration_basis` обязателен в каждой спецификации; QA проверяет той же линейкой |
| «У собственных текстов нет внешней проверки» | Это ровно роль `content-qa-agent`; `validated` без неё недостижим |
| Банк теста весь про собеседования | Ограничение «тематически нейтрально» живёт в спецификации (режим `assessment-bank`) и проверяется по пункту goal alignment |
| `into a` → падение заливки, 4 раза | Content Agent не пишет SQL вообще; экранирование и сторож — в `content-emit` |
| Файлы по 12–14 КБ находили ошибку за минуту | Нарезка встроена в эмиттер, а не в дисциплину автора |
| `missionFromContent` жёстко ставит 5 заданий | `content_budget.tasks_per_lesson` из `onboarding-v2.md §7.1` — вход генератора |
| Пустые темы (`clothing`, B2+) | `topic-coverage-report` делает пробел входом Learning Agent, а не наблюдением в отчёте |
| Черновики доезжают до пользователя | Фильтр `status = 'validated'` у потребителей (§5.6) |

## **12. Режимы отказа**

Что может пойти не так именно в **этой** конструкции, и что с этим сделано:

| Риск | Митигация |
| ----- | ----- |
| QA превращается в штамп «APPROVED» | Вердикт обязан перечислить все 12 пунктов чек-листа с исходом по каждому; пустой список findings при `APPROVED` допустим, а неотвеченный пункт — нет |
| QA придирается бесконечно | Лимит 2 раундов (§9.2); severity обязателен — `minor` не блокирует `APPROVED`, блокирует только `blocker` |
| Content подгоняет ответ под рецензента | Memory QA не передаётся Content Agent (§8) |
| Learning Agent пишет невыполнимые спецификации | `SPEC_INFEASIBLE` — легальный исход, а не провал; повторяющиеся случаи копятся в его `episodic.md` |
| Спецификации расходятся с содержимым базы | `spec_id`/`objective_id` в БД (§5.5) — иначе связь живёт только в git и рвётся при первой ручной правке |
| Три агента дороже одного прохода | Дороже — сознательно. Материал, попавший к ученику, стоит дороже токенов; и gate B снимает с QA всё механическое |
| Ростер расползётся до шести | §1: новый агент — только под ответственность, которой ни у кого нет. Новый тип задания — это Skill |

## **13. Решения по открытым вопросам**

Все шесть закрыты 2026-08-28. Записаны здесь вместе с ценой — решение без
названной цены через месяц выглядит как очевидность, которой оно не было.

**1. Миграция под прослеживаемость — да.**
`supabase/migrations/20260828160000_content_provenance.sql`: `content_units.spec_id`,
`knowledge_items.objective_id`, `generated_exercises.objective_id`, плюс
`assessment_questions.cefr_level`/`knowledge_item_id`/`spec_id`/`objective_id`
(последние две колонки этап 3 плана и так требовал). Все nullable — 103 главы
Open Oregon импортированы до появления спецификаций, и придумывать им
спецификацию задним числом значило бы записать неправду как данные.
Цена: одна дополнительная миграция и уникальный индекс на
`assessment_questions (language, prompt)`, который **упадёт**, если в банке уже
есть дубли. Это намеренно: два одинаковых вопроса в измерительном инструменте —
дефект, и лучше узнать о нём при миграции.

**2. Фильтр `status = 'validated'` — включён, в правильном порядке.**
Сначала одобрена и сгенерирована первая партия
(`supabase/seed-authored-clothing.sql`), затем добавлен фильтр в
`missionFromContent()`. Реализация вскрыла деталь, которой не было в дизайне:
фильтровать надо **до** выбора главы (см. §5.6).
Цена названа честно: весь ранее залитый материал сейчас `draft` и в миссии не
попадает. Фолбэк на `generateMission` не даёт ничему сломаться.

**3. Ретроспективная проверка уже залитого — партиями, не разом.**
103 главы Open Oregon и первая authored-партия проходят пайплайн в режиме
`imported` по мере надобности: сначала то, что реально нужно ближайшим целям.
Ставить всё в очередь до первого нового пакета значило бы заморозить контент на
недели. Записано в `docs/plan-tasks.md` как отдельная задача.

**4. Модель для ролей — QA не слабее автора.**
Рецензент на более слабой модели систематически не увидит того, что автор
сделал, и вернёт APPROVED там, где смотреть было нечем. Это делает всю
конструкцию декоративной. Конкретную модель выбирает пользователь при запуске;
в карточках агентов `model` намеренно не зафиксирован, чтобы не прятать это
решение в frontmatter.

**5. Таксономия тем — меняется только вручную.**
Learning Agent может *предложить* новую тему, но не добавить её. Причина в самой
таксономии: она описывает, что нужно ученику, а не что удобно сгенерировать
(`supabase/seed-topics.sql`). Агент, которому нечем закрыть тему, имеет прямой
стимул завести тему поудобнее — и пустая тема перестанет быть сигналом.
Зафиксировано в Boundaries `learning-agent`.

**6. Язык: спецификации и ревью по-русски, контент по-английски.**
Так же, как остальная документация проекта. Учебный материал внутри артефактов —
на целевом языке ученика.

## **14. Порядок реализации**

Порядок выведен по тому же принципу, что `AGENT_FRAMEWORK.md §14`: сначала
настоящая работа, потом формализация роли — чтобы Boundaries писались по
реальному опыту, а не вслепую.
