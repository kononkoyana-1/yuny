# `docs/design/` — решения по UI до того, как они стали кодом

Здесь живут артефакты цикла из двух агентов. Полный протокол —
`docs/DESIGN_LOOP.md`; этот файл отвечает только на вопрос «что куда класть».

```
specs/<slug>.design.md      ui-designer, gate A — что и почему строим (§5.1)
reviews/<slug>.review.md    ui-designer, gate B — вердикт, раунды дописываются снизу (§5.2)
```

`<slug>` один на всю цепочку: `<экран>-<что-делаем>`, например
`home-mission-card`. По имени видно, какая спецификация породила какое ревью.

## Правила, которые легко нарушить

- **Значения — именами токенов, не литералами.** Сырой `#7B6BD6` или `24px` в
  спецификации — дефект спецификации. Токены — существующие из
  `apps/mobile/shared/config/tokens.ts` или новые, объявленные в разделе спеки
  «Новые токены» со значениями для обеих тем.
- **Текущий вид приложения — не образец** (решение владельца 2026-09-24).
  Раскладку и визуальный язык дизайнер решает сам: сочно, современно, по
  канонам UX/UI. `assets/image/design.png` — история старого интерфейса.
- **Раунды ревью дописываются снизу, а не переписываются.** История того, что
  было отклонено и почему, — это то, из чего растёт `semantic.md` агентов.
- **Спека v2 — это новый файл-версия внутри того же `<slug>.design.md`
  с заголовком `v2`, а не молчаливая правка v1.** Иначе разработчик оказывается
  виноват в невыполнении требования, которого в момент работы не существовало.

## Чего здесь **нет**

Кода. `ui-designer` не редактирует ничего в `apps/mobile/**` — ни экран, ни
токен, ни «одну строчку». Найденный дефект чинит `frontend-builder`,
недостающий примитив делает `design-system-agent`.
