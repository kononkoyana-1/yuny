# Онбординг v2 — от заявленного уровня к дорожной карте

> **Статус:** проект логики, до кода.
> **Отношение к TZ.md:** дополняет §8 (экраны 01–08), §5 (модель данных), §6 (контракт).
> Расхождения с зафиксированными решениями вынесены в §8 — они требуют явного решения, а не молчаливой реализации (TZ.md §21.2, правило 4).
> **Основание:** прогон текущего онбординга 2026-08-27 (см. §1).

---

## 1. Что показал прогон текущего онбординга

Приложение проведено вживую от Welcome до Home с целью «путешествовать по Европе».

| Наблюдение | Причина в коде |
| --- | --- |
| Уровень языка не спрашивается нигде | `goal-setup.tsx` — три поля: цель, дедлайн, минуты |
| Тест не связан с целью: вопросы про собеседования при цели «путешествия» | `assessment-next` читает банк `order by position`, цель не участвует в выборке |
| Тест не адаптивный, 4 вопроса, только vocabulary/grammar/reading | там же; `difficulty` в выборке не используется |
| Итоговая миссия — «Practice interview answers» для цели про путешествия | наследует перекос теста через `skill_states` |
| Непроверенные навыки получают уровень по фиксированной таблице | `assessment-complete`: `baseline * UNTESTED_DISCOUNT` (listening 0.9, writing 0.75, speaking 0.65) |

Последнее — структурная проблема, а не случайность: среди непротестированных навыков listening **всегда** окажется сильнейшим, а speaking — слабейшим, у любого пользователя. При этом `stronger_skill` выбирается по всем шести навыкам, включая неизмеренные, а `needs_work` — только по протестированным.

**Вывод.** Онбординг сейчас собирает недостаточно входных данных, чтобы построить что-либо персональное, и тест не является измерением.

## 2. Что онбординг обязан произвести на выходе

Онбординг заканчивается тем, что в системе есть:

1. **Goal** — цель, дедлайн, бюджет времени (уже есть);
2. **Declared CEFR** — что пользователь сам о себе заявил (нет);
3. **Assessed CEFR** — что подтвердил тест, с мерой уверенности (нет);
4. **Learning State** — уровни по навыкам (есть, но частично выдуманные);
5. **Roadmap** — упорядоченные тематические модули до цели (нет);
6. **Первая Mission** — первый урок внутри первого модуля (есть, но не привязан к модулю).

## 3. Модель данных — что добавляется

### 3.1 Уровень CEFR

```sql
create type public.cefr_level as enum ('A1','A2','B1','B2','C1','C2');

-- Заявлено пользователем на экране 03.
alter table public.goals
  add column declared_cefr public.cefr_level,
  -- Языковой порог самой цели. Решает goal-analyze, не клиент (TZ.md §3, правило 1).
  add column required_cefr public.cefr_level;

-- Подтверждено тестом.
alter table public.learning_states
  add column assessed_cefr    public.cefr_level,
  add column cefr_confidence  numeric(4,3) check (cefr_confidence between 0 and 1);
```

**Почему CEFR — свойство ученика, а не каждого навыка.** `skill_states.level` (0–1) остаётся единственной точной величиной и продолжает выбирать фокусный навык. CEFR решает три отдельные задачи: выбрать сложность теста, отобрать контент, и сказать «нужен базовый курс». Все три — про ученика целиком. Дублировать 0–1 более грубой шкалой на каждый навык смысла нет.

### 3.2 Разметка контента по уровню и теме

```sql
alter table public.content_units
  add column cefr_level public.cefr_level;

-- Канонические темы, общие для всех учебников.
create table public.topics (
  id         uuid primary key default gen_random_uuid(),
  slug       text not null unique,
  label      text not null,
  created_at timestamptz not null default now()
);

create table public.content_unit_topics (
  content_unit_id uuid not null references public.content_units (id) on delete cascade,
  topic_id        uuid not null references public.topics (id)        on delete cascade,
  primary key (content_unit_id, topic_id)
);
```

**Ключевое решение: темы канонические, а не привязанные к учебнику.** Иначе модуль «транспорт» окажется просто «главы 4–6 книги №1», и мы получим ту же болезнь, что уже вылечили в `mission-generate`: порядок учебника вместо потребностей ученика. Канонические темы позволяют одному модулю тянуть материал из нескольких книг.

**Темы ситуативные, а не предметные — решение от 2026-09-08.** `seed-topics.sql` описывал предметные области («Food and cooking», «Travel and accommodation», «Shopping and money»). Для каталога это верная форма, для модуля — нет: ученик не собирается «изучать еду», он собирается заказать в ресторане, заселиться в отель, снять квартиру, купить продукты. Модуль «Shopping and money» не может сказать, что ученик будет уметь в конце.

Сами главы давно написаны ситуативно — «Booking a place to stay», «Wu buys food», «Ann visits the market»; ситуативной не была только таксономия над ними. Это исправляет `supabase/seed-situational-topics.sql`: добавляет ситуации, перевешивает на них существующие главы и снимает с этих же глав предметный тег, который ситуация заменила, — иначе одна глава кормила бы две темы, конкурирующие за место на одном маршруте. Предметные темы остаются в таксономии и держат весь остальной контент: работе, истории и мнениям ситуации не подобрать.

Добавление темы не создаёт модуль. `readCoverage` пускает тему в маршрут только там, где под неё есть проверенные `knowledge_items` на нужной полосе, — поэтому «в ресторане» не появится ни у кого, пока под неё не написан материал. Список тем без покрытия и есть список того, что писать дальше.

### 3.3 Дорожная карта

```sql
create table public.roadmap_modules (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references auth.users (id)     on delete cascade,
  goal_id     uuid not null references public.goals (id)   on delete cascade,
  topic_id    uuid          references public.topics (id)  on delete set null,
  position    integer not null,
  title       text    not null,
  why         text    not null,          -- зачем этот модуль для этой цели
  target_cefr public.cefr_level not null,
  kind        text not null default 'topic'
                check (kind in ('foundation','topic')),
  status      text not null default 'locked'
                check (status in ('locked','available','in_progress','completed')),
  created_at  timestamptz not null default now(),
  unique (goal_id, position)
);

alter table public.missions
  add column roadmap_module_id uuid references public.roadmap_modules (id) on delete set null;
```

Права клиента: SELECT своих строк. Запись — только через Edge Function (TZ.md §3, правило 3).

### 3.4 Связь Evidence с конкретной единицей знания

```sql
alter table public.evidence
  add column knowledge_item_id uuid references public.knowledge_items (id) on delete set null;
```

**Без этого «урок включает слабые места пользователя» нереализуем.** Сейчас `evidence` знает, что ученик слаб в vocabulary — но не знает, что он слаб в слове «departure». Повторение нельзя нацелить на то, чего система не записала.

### 3.5 Банк тестовых заданий из учебников

```sql
alter table public.assessment_questions
  add column cefr_level        public.cefr_level,
  add column knowledge_item_id uuid references public.knowledge_items (id) on delete set null;
```

Задания не читаются из `generated_exercises` напрямую во время теста. Вместо этого валидированные упражнения **промотируются** в `assessment_questions` отдельным шагом пайплайна. Так у теста остаётся один источник чтения и один формат, а происхождение задания сохраняется через `knowledge_item_id`.

### 3.6 Состояние адаптивной сессии

```sql
create table public.assessment_sessions (
  id              uuid primary key default gen_random_uuid(),
  user_id         uuid not null references auth.users (id)   on delete cascade,
  goal_id         uuid not null references public.goals (id) on delete cascade,
  declared_cefr   public.cefr_level not null,
  current_cefr    public.cefr_level not null,
  served_count    integer not null default 0,
  started_at      timestamptz not null default now(),
  ended_at        timestamptz,
  budget_seconds  integer not null default 600,
  status          text not null default 'active'
                    check (status in ('active','complete','abandoned'))
);
```

Лестница адаптации — образовательное решение, поэтому её состояние живёт на сервере, а не в сторе клиента (TZ.md §3, правило 1).

## 4. Онбординг по экранам

Новых экранов нет. Изменения — внутри существующих 01–08, что соответствует `MVP-4.01` и `MVP-4.12`.

| # | Экран | Что меняется |
| --- | --- | --- |
| 01 | Welcome | без изменений |
| 02 | Target Language | без изменений |
| 03 | Goal Setup | **+ четвёртое поле: «Ваш уровень»** (A1–C2 + «не знаю») |
| 04 | Goal Analysis | + показывает `required_cefr` и темы, которые цель подразумевает |
| 05 | Goal Confirmation | без изменений |
| 06 | Initial Assessment | **переписан: адаптивный, из учебников, ≤ 10 мин** |
| 07 | Assessment Result | **+ подтверждённый уровень против заявленного; вердикт про базовый курс** |
| 08 | Learning Strategy | **становится превью реальной дорожной карты** |

### 4.1 Экран 03 — «не знаю» как первый класс

Вариант «не знаю» обязателен: заставлять новичка выбирать между A2 и B1 — это спрашивать то, чего он не знает. При «не знаю» тест стартует с A2 и просто расширяет диапазон поиска.

### 4.2 Экран 07 — три возможных исхода

1. **Подтверждено** (`assessed == declared`) — «Вы верно оценили себя».
2. **Скорректировано** (расхождение на 1 ступень) — спокойно называем реальную точку старта.
3. **Нужен фундамент** (`assessed` ниже `required_cefr` на ≥ 2 ступени) — сообщаем, что до цели нужен базовый курс.

Тон по TZ.md §14: не «вы провалились», а «начнём с фундамента — так до цели быстрее». Никаких процентов и баллов на экране.

## 5. Алгоритм адаптивного теста

**Бюджет:** ≤ 10 минут, ≤ 15 заданий (≈ 40 с на задание).

**Фаза 1 — обязательный охват трёх уровней (9 заданий).**
По 3 задания на `declared-1`, `declared`, `declared+1`. Это прямо реализует требование «ниже, по уровню и выше» и гарантирует, что вердикт не построен на одной полосе. Задания внутри блока распределяются по навыкам, которые нужны цели.

**Фаза 2 — уточнение границы (до 6 заданий).**
Правило шага по результату блока из трёх:

| Результат блока | Действие |
| --- | --- |
| 3/3 | ступень вверх (если не C2) |
| 2/3 | полоса — кандидат на вердикт, остаться |
| 0/3 или 1/3 | ступень вниз (если не A1) |

**Остановка:** полоса подтверждена (посещена дважды с результатом ≥ 2/3), либо исчерпаны 15 заданий, либо истекли 10 минут.

**Вердикт:** `assessed_cefr` = наивысшая полоса с долей верных ≥ 2/3.
`cefr_confidence` растёт от числа заданий на решающей полосе.

**Навыки, которые тест не покрывает — РЕШЕНО 2026-08-27.** Speaking и writing текстовым тестом не измеряются. Нынешняя таблица скидок `UNTESTED_DISCOUNT` в `assessment-complete` **удаляется**: `skill_states.confidence` для неизмеренных навыков ставится в 0, а экран 07 их **не называет** ни сильными, ни слабыми. Система не утверждает того, чего не проверяла. Уровни этих навыков уточняются позже, из реального Evidence.

Следствие для `summarizeAssessment`: `stronger_skill` больше нельзя выбирать по всем шести навыкам — только по протестированным, как уже делает `needs_work`.

## 6. Построение дорожной карты

Выполняется в фоновом задании `assessment-complete`, сразу после вердикта — чтобы у пользователя был один экран ожидания, а не два.

**Вход:** цель (title, outcomes, target_situations, `required_cefr`), `assessed_cefr`, доступные темы с их покрытием контентом.
**Выход:** упорядоченные `roadmap_modules`.

**Правила отбора:**
1. Темы, релевантные цели, — из `target_situations` цели, сопоставленных с канонической таксономией тем;
2. Только темы, у которых **реально есть контент** на полосах от `assessed_cefr` до `required_cefr`;
3. Если `assessed_cefr` ниже `required_cefr` на ≥ 2 ступени — впереди ставятся модули `kind='foundation'`;
4. Порядок: по возрастанию `target_cefr`; внутри одной полосы фундамент идёт перед темами, темы — по релевантности цели.

**Правило 4 изменено 2026-08-29** (было: «сначала фундамент, дальше по возрастанию `target_cefr`»). Прежняя формулировка ставила **весь** фундамент в начало, и на живом прогоне это дало маршрут, который читается как ошибка: ученик A2 с целью B2 получал «Foundations: A2», «Foundations: B1», а следом две темы на A2 — то есть поднимись до B1 и вернись к материалу A2. Каждый модуль по отдельности был правильным, последовательность — нет. Фундамент по-прежнему решает правило 3; полоса решает только его место.

При обрезке до потолка модулей режутся темы, а не фундамент: фундамент структурен — правило 3 поставило его потому, что без него цель недостижима, — а восьмая тема наименее релевантна из всего маршрута.

**Статусы:** доступен ровно один модуль (`in_progress`), следующий — `available`, остальные `locked`. Модуль закрывается, когда закрыты его уроки.

**Уроков в модуле — 20** (`MISSIONS_PER_MODULE` в `_shared/roadmap.ts`, решение от 2026-09-08). Модуль — это ситуация («в отеле», «снимаем квартиру»), и ситуация стоит серии уроков, а не одного. Переход делает `advanceRoadmap`, который вызывается из `activity-submit` в момент, когда закрылась последняя активность миссии: текущий модуль получает `completed`, следующий по `position` — `in_progress`, следующий за ним — `available`.

Раньше переходов не было вовсе: `buildRoadmap` ставил нулевому модулю `in_progress`, и больше ни одна функция статусы не писала. Привязка миссии к модулю при этом работала — и пожизненно указывала на первый модуль, то есть карта не двигалась. Это то же самое, что не иметь карты.

Проверять прогресс именно после завершения миссии, а не при генерации следующей, — сознательно: спросив при генерации, карта отставала бы на урок и показывала ученику модуль, который он уже прошёл.

«Базовый курс» — это не отдельный продукт, а модули `kind='foundation'` в начале той же карты. Отдельной сущности не заводим.

## 7. Размер и состав урока

### 7.1 Размер

Миссия — это **15–20 заданий** за один заход. `MISSION_MIN_TASKS` / `MISSION_MAX_TASKS` в `_shared/mission.ts` — единственное место, где это число живёт; все три пути сборки миссии (AI, контентный, детерминированный) меряются им.

**Размер урока изменён 2026-09-08** (было: «3–5 заданий на 5–7 минут», при `lessons_per_day = max(1, round(daily_minutes / 6))` — 30 мин/день ≈ 5 уроков).

Прежняя модель считала день цепочкой из нескольких коротких уроков, и внутри этой модели 3–5 заданий были правильным числом. Но `lessons_per_day` так и не был реализован: `mission-generate` выдаёт **одну** миссию, и следующая появляется только по новому запросу — цепочки нет. В результате день ученика фактически равнялся одному уроку, и на живом прогоне это дало миссию из четырёх заданий, которая не читается как занятие.

Изменено именно число заданий, а не решение о коротких уроках: если `lessons_per_day` появится, вернуться к 3–5 нужно будет вместе с ним, одним изменением. Пока цепочки нет, миссия обязана быть занятием целиком.

Что из этого следует для сборки:

* **Контентный путь больше не добивает миссию синтетикой.** `vocabulary_choice` из извлечённых слов и «какая это тема?» задают один и тот же вопрос с разными вариантами: два таких задания из пяти — допустимая подпорка, двенадцать из двадцати — это и есть миссия. Потолок — `MAX_SYNTHETIC_TASKS`; глава, которой не хватает своих проверенных упражнений, отдаёт `null`, и миссию пишет AI по теме модуля.
* **Правильный вариант в multiple choice больше не стоит первым.** Раньше все детерминированные MC собирались как `correct_index: 0`. На трёх заданиях это незаметно, на двадцати — стратегия: ученик, который всегда жмёт первый вариант, получает полный балл.
* **Экран миссии продолжает с места остановки.** До этого он всегда начинал с нулевого задания; на четырёх заданиях это терпимо, на двадцати означает, что ученик после перезахода отвечает заново на уже оценённое.

### 7.2 Состав

Каждый урок собирается из трёх источников:

| Доля | Что | Источник |
| --- | --- | --- |
| ~60% | новый материал текущего модуля | `knowledge_items` темы модуля |
| ~25% | повтор того, где ученик ошибался | `evidence` со слабым результатом → `knowledge_item_id` |
| ~15% | проверка удержания давно верного | `evidence` с сильным результатом, старше N дней |

Для миссии из 20 заданий это ~12 новых, ~5 на повтор ошибок и ~3 на удержание. Пропорции — серверное решение, клиент их не вычисляет.

Ни одна из трёх долей пока не реализована: миссия целиком собирается из первой строки таблицы. Вторая и третья требуют `evidence.knowledge_item_id` (§3.4), которого ещё нет, — и до тех пор длинная миссия остаётся двадцатью заданиями по новому материалу, без интервального повторения.

Именно этот раздел опирается на §3.4: без `evidence.knowledge_item_id` вторая и третья строки таблицы нереализуемы.

## 8. Расхождения с зафиксированными решениями — требуется решение

### 8.1 Дорожная карта на Home против «one best next action» — РЕШЕНО

TZ.md §7 отклоняет вкладку «Learn» словами «каталог уроков противоречит принципу *one best next action*», а MVP Spec §40.3 запрещает числовой прогресс как главный показатель.

**Решение принято 2026-08-27:** карта — это **обзор пройденного пути, а не меню выбора**. Модули отображаются, но из них **нельзя выбрать урок** — следующее действие по-прежнему одно и назначается системой. Прогресс показывается положением в карте, а не процентами.

Кликабельная карта нарушает `MVP-3.01` по существу. Граница зафиксирована: read-only.

### 8.2 Длина теста — РЕШЕНО

**Решение принято 2026-08-27: остаётся 15 заданий / 10 минут** (9 обязательных + до 6 уточняющих), как описано в §5. Сокращённый вариант на 10 заданий отклонён.

### 8.3 Поле уровня на экране 03

Формально экран 03 в TZ.md §8 описан как «свободный текст + Deadline + Available Time». Четвёртое поле — вариация внутри экрана (`MVP-4.12`), не новый экран, но это всё же правка описанного экрана.

### 8.4 Вердикт «нужен базовый курс»

В TZ.md такого понятия нет, но есть feasibility и «предложенные корректировки» в `goal-analyze` (§6). Предлагается трактовать вердикт как частный случай корректировки цели, а не как новую сущность.

## 9. Главный риск — контента почти нет (измерено)

Инвентарь базы на 2026-08-27:

| Показатель | Значение |
| --- | --- |
| Источников | 1 — «A Digital Workbook for Beginning ESOL», CC BY 4.0 |
| Единиц контента | 36 (30 глав), все `parsed` |
| **Слов во всём источнике** | **5 571** (в среднем 155 на главу, максимум 823) |
| Блоков | 246 абзацев (≈20 слов), 110 упражнений (≈29 знаков), 66 заголовков |
| Knowledge items | 242: **195 example, 36 topic, 6 grammar, 5 vocabulary** |
| Сгенерированных упражнений | **11** (5 fill_blank, 6 multiple_choice) |
| Банк ассессмента | 12 вопросов |

### 9.1 AI-извлечение ни разу не отрабатывало

**Все 242 knowledge items имеют `origin = 'source_derived'`. Записей `ai_generated` — ноль.**

Значит `content-import` работал при `aiAvailable() === false`, и всё сделал детерминированный фолбэк из `_shared/content.ts`: тема = сама глава (36 штук, механически), grammar = заголовки глав, похожие на грамматические правила (6), vocabulary = единственный список слов, который удалось найти механически (5), example = предложения дословно (195).

Из 30 глав хоть что-то дали **7**, а словарь есть ровно в одной — «Greetings» (5 слов, 5 упражнений). Остальные шесть дали по одному грамматическому пункту и одному упражнению.

Это **чинится конфигурацией, а не кодом**: 246 абзацев живого текста детерминированный извлекатель просто проигнорировал. Повторный прогон импорта с ключом AI даст с тех же 36 глав кратно больше. Самая дешёвая победа во всём плане.

### 9.2 Но источник всё равно слишком тонкий

5 571 слово — это примерно 11 страниц текста, и это **рабочая тетрадь для начинающих**, а не учебник: 110 из 422 блоков — короткие задания-подсказки по 29 знаков.

Даже при идеальном извлечении отсюда невозможно получить:

* **уровни выше A2** — источник целиком начальный, а тест «ниже / по уровню / выше» требует минимум трёх полос;
* **тематическое разнообразие** — карта из одной темы («Greetings») вырождается в один модуль;
* **языки, кроме английского** — в UI предлагается четыре.

**Вывод: этап 1 плана — это не разметка имеющегося, а получение недостающего.** Порядок работ начинается с контента, иначе мы построим онбординг, которому нечего показать.

## 10a. Источники-кандидаты — лицензии проверены 2026-08-28

Проверено обращением к самим источникам, а не к каталожным карточкам. Важно: на страницах каталога Open Textbook Library всегда присутствует ссылка «CC BY 4.0» — это футер самого каталога. Лицензия книги лежит в поле **Conditions of Use**, и она может отличаться.

| Книга | Лицензия (проверено) | Импорт | Уровень |
| --- | --- | --- | --- |
| Green Tea Intermediate English Communication OER | **CC BY 4.0** — из `pressbooks/v2/metadata` самой книги | Pressbooks API, 8 частей / **45 глав** | Intermediate (≈B1) |
| Portland People and Places | **CC BY 4.0** — из metadata | Pressbooks API, **9 глав** | Reader |
| Home and School | **CC BY 4.0** — из metadata | Pressbooks API, **10 глав** | Reader |
| Advanced Academic Grammar for ESL Students | **CC BY 4.0** (Rebecca Al Haider) | ⚠️ **не Pressbooks** — Google Docs / PDF / Word | Advanced |
| Writing for Change: An Advanced ELL Resource | **CC BY** — «Conditions of Use: Attribution» | ⚠️ требует проверки хостинга | Advanced |
| English Composition: Connect, Collaborate, Communicate | **CC BY** — «Conditions of Use: Attribution» | ⚠️ требует проверки хостинга | Advanced |
| Brehe's Grammar Anatomy | **CC BY-SA** — «Conditions of Use: Attribution-ShareAlike» | ⚠️ требует проверки хостинга | Advanced |

**Шесть из семи свободны для коммерческого использования**, седьмая (Brehe) — с оговоркой ShareAlike, см. ниже.

### 10a.0 Отклонено по лицензии

Проверено 2026-08-28 через `pressbooks/v2/metadata` самих книг:

| Книга | Лицензия | Почему нельзя |
| --- | --- | --- |
| Evergreen (Intermediate) | **CC BY-NC-SA** | NC запрещает коммерческое использование; SA заставляет открывать производные |
| Evergreen (Advanced) | **CC BY-NC-SA** | то же |

Обе были бы очевидным выбором для intermediate и advanced — и обе непригодны. Бесплатный тариф коммерческого продукта NC не спасает: оценивается характер использования, а не оплатил ли конкретный пользователь.

**Каталогам доверять нельзя, лицензию читать у первоисточника.** Два случая в одном дне: на страницах Open Textbook Library ссылка «CC BY 4.0» в футере каталога маскирует настоящую лицензию книги, а для «Writing for Change» каталог показывает CC BY, тогда как издатель (Whatcom CC) публикует под CC BY-NC-SA. Авторитетный источник — метаданные самой книги.

### 10a.1 Brehe's Grammar Anatomy — единственный с ShareAlike

CC BY-SA требует, чтобы производные работы распространялись на тех же условиях. Наш пайплайн производит именно производные: `knowledge_items` и `generated_exercises`, извлечённые из текста книги. Это означает, что упражнения, выведенные из Brehe, с высокой вероятностью придётся публиковать под CC BY-SA.

Практический вывод: **либо не берём Brehe вовсе** (шесть остальных книг покрывают ту же грамматику под CC BY), **либо изолируем** его производные — отдельный `content_source` с пометкой лицензии и запрет смешивать его материал в одной единице с CC BY-контентом. Первый вариант проще и я бы выбрал его: выгода не стоит юридической связанности.

### 10a.2 Оговорка «except where otherwise noted»

Все три книги Open Oregon содержат стандартную формулировку Pressbooks «…is licensed under CC BY 4.0, **except where otherwise noted**». Отдельные главы могут иметь свою лицензию. При импорте нужно читать лицензию на уровне главы, а не только книги, и складывать её в `content_units`.

### 10a.3 Сколько контента это реально даёт — измерено 2026-08-28

Все три книги выкачаны и разобраны целиком (67 единиц, ноль ошибок), поэтому цифры точные, а не оценочные.

| Источник | Глав | Слов | Медиана на главу |
| --- | --- | --- | --- |
| A Digital Workbook for Beginning ESOL (был) | 30 | 5 571 | — |
| Green Tea Intermediate | 45 | **3 017** | **32** |
| Portland People and Places | 9 | 2 402 | 258 |
| Home and School | 10 | 1 770 | 169 |
| **Итого** | **94** | **12 760** | |

**Вторая полоса уровня не появилась.** Green Tea заявлена как intermediate, но это курс вокруг видео и аудио: медиана 32 слова на главу, девять глав почти пустые, текст — только подсказки и инструкции. Как источник учебного текста она непригодна.

Зато два ридера, которые выглядели второстепенными, дали лучший материал корпуса: связные тексты и диалоги по 150–500 слов. Они закрывают A1–A2.

**Итог по полосам:** A1–A2 покрыт, B1 не покрыт ничем, B2–C1 упирается в лицензии и отсутствие адаптера. Отсюда решение наполнять банк теста генерацией (см. `plan-tasks.md`, этап 2).

### 10a.4 Следствие для плана

Существующий импортёр умеет **только Pressbooks** (`_shared/content.ts`, `ADAPTERS = { pressbooks }`). Поэтому:

* три книги Open Oregon импортируются **без единой строчки кода** — только три строки в `content_sources` с нужным `book_slug`, ровно как обещает комментарий в адаптере;
* четыре книги UMN требуют **нового адаптера** (PDF/DOCX/Google Docs) — это отдельная работа, и её объём стоит оценить до того, как обещать продвинутую полосу.

## 11. Открытые вопросы

1. **Таксономия тем** — фиксированный список или растёт по мере импорта учебников?
2. **Уровень цели** — `required_cefr` определяет AI по формулировке цели, или берётся из таблицы соответствий «тип цели → уровень»?
3. **Пересдача теста** — можно ли перепройти ассессмент позже, и что тогда происходит с уже построенной картой?
4. **Пересборка карты** — карта строится один раз или перестраивается, когда Evidence показывает, что реальный уровень разошёлся с вердиктом?
5. **Speaking/writing** — измерять ли их в онбординге вообще, или честно оставлять неизвестными до первых реальных заданий?
6. **Длина теста** — см. §8.2.
